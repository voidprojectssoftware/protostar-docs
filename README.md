# protostar-docs

The unified documentation hub for **Protostar**. This repo owns the site —
theme, navigation, landing page — and stitches together docs that live next to
the code in each product repo.

The guiding idea: **docs are authored where the code is, and presented in one
place.** Authors never leave their product repo to write docs. This hub lifts
each product's `docs/` folder in at build time and renders it as one site.

```
                 docs.manifest.json
                 (lists product repos)
                         │
   ┌─────────────────────┼─────────────────────┐
   │                     │                      │
voidprojectssoftware/protostar   …future repos…   docs-hub/  (this repo's own docs)
   │  docs/  ────────────┐                      │
   └─────────────────────┤  fetch-docs.mjs      │
                         ▼  (git sparse-checkout / local copy)
                    external/<id>/docs
                         │
                         ▼
                 Docusaurus multi-instance build
                         │
                         ▼
               one site, one navbar, per-product sidebars
```

## How it works

1. **`docs.manifest.json`** is the single source of truth. Each entry names a
   product repo, the branch/tag to lift docs from, and the URL path to serve
   them under. Adding a product is a one-line change here.
2. **`scripts/fetch-docs.mjs`** populates `external/<id>/docs` for every product
   before a build. In CI it does a fast `git sparse-checkout` of only that repo's
   `docs/` folder at the pinned ref. Locally, if you have the product repo
   checked out as a sibling folder, it copies from there so you can preview
   unpublished edits.
3. **`docusaurus.config.ts`** reads the manifest and generates one
   [Docusaurus docs plugin instance](https://docusaurus.io/docs/docs-multi-instance)
   per product — each with its own route, autogenerated sidebar, and an "edit
   this page" link that points back to the source repo.
4. **`external/` is gitignored.** Content is fetched fresh each build; the
   product repo stays the single source of truth.

## Local development

```bash
npm install
npm start          # fetches docs, then runs the dev server
```

`npm start` runs `fetch-docs` first. If the product repos are checked out as
siblings (e.g. `../protostar`), their `docs/` are copied in so you see your local
edits. Otherwise the docs are pulled from GitHub at the manifest's pinned ref.

To force one mode or the other:

```bash
node scripts/fetch-docs.mjs --remote   # always pull from GitHub
node scripts/fetch-docs.mjs --local    # always copy from sibling checkouts
npm run start:no-fetch                 # reuse whatever is already in external/
```

Build the static site:

```bash
npm run build      # fetch-docs + docusaurus build  ->  ./build
```

## Adding a new product's docs

1. In that product repo, create a `docs/` folder of Markdown/MDX (see
   [CONTRIBUTING.md](CONTRIBUTING.md) for conventions).
2. Add one entry to `docs.manifest.json`:
   ```json
   {
     "id": "my-product",
     "label": "My Product",
     "repo": "voidprojectssoftware/my-product",
     "ref": "main",
     "docsPath": "docs",
     "routeBasePath": "my-product"
   }
   ```
3. Done. The navbar, sidebar, routing, and edit links wire up automatically.

## Hosting

This repo is **public and intentionally host-agnostic** — it contains no deploy
workflow, no host config, and no secrets. How and where the site is hosted is
kept in a separate private repo. See [DEPLOYMENT.md](DEPLOYMENT.md) for the
architecture and the reasoning.

## Why this approach

We evaluated git submodules, a per-repo CI "push into the hub" model, the
`docusaurus-plugin-remote-content` plugin, and this sparse-checkout + multi-
instance model. This one keeps the author workflow simplest (edit Markdown next
to code, normal PR review in the product repo), keeps this repo a clean
orchestrator with no duplicated content, and avoids depending on a lightly
maintained third-party plugin. See [DEPLOYMENT.md](DEPLOYMENT.md) for the full
rationale and trade-offs.
